# 精臣标签小程序发布清单

文档状态：未放行

## 1. 当前结论

当前只能判定为“工程候选版，生产未放行”。开发过程曾取得本地自动化通过记录，但主线仍在收口，必须在候选 commit 冻结后重跑并归档，不能把过程输出当作最终发布证据。

已有的开发过程记录（非冻结候选的最终发布证据）：

- 源应用在审计时自动化通过，可作为迁移行为参考；具体数量只在对应归档中记录，不证明小程序平台一致。
- 目标小程序开发过程中 `npm run verify` 有通过记录，但测试数、文件数、事件绑定、资源引用和包体会随主线变化；最终值以冻结候选提交的最新输出为准。
- 覆盖率以同一冻结提交的 `npm run test:coverage` 最新输出为准。它只统计 Node 实际加载的纯逻辑、服务模块和有限页面方法，不含 WXML 交互、微信基础库、相机扫码、Canvas 真机差异或物理打印。
- BLE mock 已覆盖超时、错误、MTU、系统连接复用、僵尸恢复、单飞、TTL、断线失效、诊断和适配器恢复等路径；这些证据不能替代真实手机与打印机测试。
- 本地资源数与主包字节必须从冻结候选的 `npm run verify` 读取；无论本地是否通过，都不能替代微信开发者工具上传包体报告。

尚未获得且必须由用户/发布团队提供或执行：正式 AppID、微信开发者工具编译/预览、iOS/Android 真机、D11/D110/B1/B21 系列实物打印、隐私/权限/类目配置、品牌与模板/素材再分发授权、体验版灰度和生产监控。

## 7. 体验版与灰度计划

建议分三阶段，不允许跳过退出条件：

| 阶段 | 范围 | 观察期 | 放量条件 | 停止/回滚条件 |
| --- | --- | --- | --- | --- |
| 内部体验版 | 产品、QA、硬件负责人，专用测试设备 | 至少 1 个业务日 | 全真机矩阵、无开放 P0/P1 | 任一数据丢失、错打/重复打印、主流程中断 |
| 邀请灰度 | 5–20 名已知用户，按机型分层 | 至少 2 个业务日 | 连接成功率、打印成功率达到团队预设阈值；无新增 P0/P1 | 失败率显著高于内部基线、合规投诉、无法恢复连接 |
| 分批生产 | 10% → 30% → 100%，每档观察 | 每档至少 4 小时或覆盖一个业务高峰 | 指标稳定、客服无聚集问题 | 任一 P0；P1 集中爆发；包/权限/审核异常 |

在灰度开始前由产品、QA 和发布负责人填写明确数值阈值。建议至少监控：启动成功、扫码取消/失败、模板/编辑器异常、连接阶段失败、握手失败、打印开始/成功/失败、重连恢复、存储失败和用户主动取消。未完成隐私披露前，以脱敏人工记录或体验版测试报告为准，不能上传扫描原文或偷偷接入事件。

## 8. 回滚方案

- 上线前保留最近一个已验证微信版本、代码 commit、依赖锁文件和资源清单；指定唯一回滚负责人和替补。
- 新版本只向前迁移本地 schema，必须保持旧版本可读取或在发布前明确不可逆风险。本版本 schema v2 回滚演练需验证项目、模板和设置仍可恢复。
- BLE 异常可先启用本地/远端受控 kill switch `ble_reconnect_off` 停止自动重连，但这只是止损，不替代提交修复版本。
- 出现错打/重复打印时立即停止放量、关闭相关入口或撤回版本；不要尝试自动重放失败队列。
- 回滚后保留用户本地项目，提供备份指导；禁止以“清空微信数据”作为常规恢复方案。
- 回滚完成后记录影响范围、开始/恢复时间、设备/固件分布、根因和防复发测试。

## 9. 上线日 Runbook

1. 发布负责人确认 commit、版本号、审核状态、回滚版本和联系表。
2. QA 复核所有门禁证据，任何未勾 P0 项都必须停止。
3. 发布体验/生产版本，仅由授权账号操作；不在聊天或日志中发送 AppSecret。
4. 用专用设备执行相机扫码建标冒烟，再执行 1 张“上线冒烟”标签：打开→模板/扫码→编辑→预检→连接→打印→历史。
5. 按灰度档位观察连接、握手、打印、存储和客服反馈；每档书面签字后再扩大。
6. 触发停止条件时先冻结放量，再按回滚方案处理，保留脱敏证据。
7. 观察窗口结束后记录最终版本、指标、遗留 P2 和复盘日期。
