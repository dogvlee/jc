# 精臣标签小程序环境与部署手册

文档状态：工程基线；平台部署待验证
适用版本：`1.0.0-rc.1`
更新日期：2026-08-11

## 1. 目的与当前结论

本文定义开发、QA、UAT 和生产四类环境，以及构建、上传、体验、灰度、发布和回滚所需的证据。它是执行手册，不代表微信平台门禁已经完成。

当前能够确认的事实：

- `package.json` 与 `package-lock.json` 版本均为 `1.0.0-rc.1`。
- `project.config.json` 的 AppID 仍为 `touristappid`，基础库配置为 `2.32.3`。
- 仓库未集成 `miniprogram-ci`、微信开发者工具 CLI 或自动上传流水线；上传必须由授权人员在受控工作站执行。
- 开发过程中 `npm run verify` 有通过记录；最终测试数、文件数和本地主包字节必须从冻结候选 commit 的最新输出归档，且不能替代微信上传包报告。
- 尚无开发者工具编译截图、体验版、审核记录、iOS/Android 真机结果或实体打印证据，因此当前状态是“工程候选版，未放行”。

## 2. 环境模型

小程序当前没有后端、账号或云同步，业务数据均在微信本地存储。环境隔离主要依赖版本通道、AppID/成员权限、测试手机、测试打印机和测试数据，而不是服务器配置。

| 环境 | 用途 | 版本载体 | 数据与设备 | 准入条件 | 当前状态 |
| --- | --- | --- | --- | --- | --- |
| dev | 日常开发、Node 测试、静态检查 | 本地代码；必要时开发版 | 合成标签、BLE mock；真实打印仅限开发专机 | `npm ci`、受影响测试、`npm run check` | 本地可用；`touristappid` 不作为发布证据 |
| qa | 完整回归、开发者工具编译、缺陷复测 | 授权 AppID 的开发版 | 专用测试账号、手机、打印机、耗材 | 全量自动化通过；候选 commit 冻结 | 正式 AppID/DevTools 证据待提供 |
| uat | 业务验收、跨平台旅程、硬件矩阵 | 体验版 | 邀请成员、脱敏业务样例、专用硬件 | QA 无开放 P0/P1；隐私和授权材料初审通过 | 未执行 |
| prod | 审核后生产使用和最小安全冒烟 | 正式发布版本 | 用户本地数据；仅用专门冒烟设备打印 1 张测试标签 | 六方门禁签字、审核通过、回滚版本可用 | 未放行 |

同一正式 AppID 可以通过开发版、体验版和正式版形成通道隔离；如果组织拥有独立 QA AppID，可进一步隔离。不得为了模拟多环境而把 AppSecret、上传私钥或生产用户备份复制进代码库。

## 3. 配置与凭据治理

### 3.1 配置清单

| 项目 | 当前值/位置 | 环境策略 |
| --- | --- | --- |
| 小程序版本 | `package.json`：`1.0.0-rc.1` | 上传版本、Git tag、发布记录三者一致 |
| AppID | `project.config.json`：`touristappid` | QA/UAT/prod 必须换成已授权 AppID，并记录变更者 |
| 基础库 | `project.config.json`：`2.32.3` | 候选版冻结；升级必须重新编译和跑真机矩阵 |
| 项目根 | `miniprogram/` | 不得把工作区提取物或源应用资源目录打入包中 |
| URL 检查 | `urlCheck: false` | 当前代码无运行时网络请求；生产候选需重新评估并记录是否可开启 |
| 本地 schema | `2` | 回滚前验证旧版本读取与备份恢复兼容性 |
| BLE kill switch | 本地键 `ble_reconnect_off` | 只用于受控设备止住自动重连；不是远程全量开关 |

### 3.2 凭据分类

- AppID 是环境标识，不等同于密钥，但仍由发布负责人管理配置变更。
- AppSecret、代码上传私钥、平台登录会话和任何签名材料均为秘密，不得写入 `miniprogram`、文档、日志、聊天记录或 Git 历史。
- 当前 `.gitignore` 已排除 `.env`、常见私钥/证书文件、`project.private.config.json` 和 `.wechat-ci/`；正式凭据仍必须只进入受控密钥库，并在提交与上传流水线运行秘密扫描。
- 发布账号实行最小权限：开发者可预览，发布负责人可上传/提交，生产发布和回滚由双人复核。禁止共享个人账号。
- 若以后引入 `miniprogram-ci`，私钥只从 CI 密钥库或受控本机读取；仓库只保存不含秘密的脚本和变量名。

## 4. 可复现构建基线

### 4.1 工具链

| 工具 | 当前依据 | 要求 |
| --- | --- | --- |
| Node.js | 本次本地验证为 v24.17.0；依赖要求 Node ≥18 | 发布团队固定一个受支持版本并写入构建记录；仓库当前未提供 `.nvmrc` |
| npm | 使用已提交 `package-lock.json` | 必须使用 `npm ci`，禁止候选构建临时升级依赖 |
| 微信开发者工具 | 未记录 | QA 首次执行前填写精确版本，并在候选期冻结 |
| 微信基础库 | `2.32.3` | 同时测试最低支持版本与目标版本；当前最低版本尚待产品确认 |
| Python/Pillow | 仅资源刷新需要，版本未锁定 | 资源刷新前固定版本和输入目录，不纳入普通发布构建 |

### 4.2 干净构建步骤

在一个不包含个人临时文件的干净 checkout 上执行：

```powershell
npm ci
npm run build:vendor
npm run verify
npm run test:coverage
```

执行规则：

1. 记录 Git commit、工作树状态、Node/npm 版本和命令输出。
2. `npm run build:vendor` 只应重建 `miniprogram/vendor/qrcode.js`；若生成意外差异，停止候选构建并查明工具链差异。
3. `npm run assets:sync` 不是普通发布步骤。它依赖同级 `niim-label-app/public/assets` 和 Pillow，仅在批准刷新素材时执行；执行后必须审查资源差异、授权清单，并以最新 `npm run verify` 记录资源引用数和包体。
4. `npm run verify` 包含项目静态检查和 Node 测试，但不包含微信编译、隐私审核、真机 UI 或实体打印。
5. `npm run check` 超过 2 MiB 会失败，达到 90% 会告警；最终限制以开发者工具上传报告和当期微信规则为准。

## 5. 候选版本产物

每个候选版本建立一份不可变发布记录，至少包含：

- 版本号、Git commit、构建时间、构建人、复核人。
- Node/npm、微信开发者工具、基础库版本。
- `npm ci`、`npm run verify`、覆盖率和本地包体输出。
- `package-lock.json`、生成的 vendor 文件、资源文件数量与哈希/变更摘要。
- 开发者工具 0 error 截图、未接受 warning 清单、上传包体报告。
- 开发版/体验版标识、体验二维码、审核单号和平台操作人。
- 手机/系统/微信版本、打印机型号/固件/耗材及样张证据链接。
- 隐私、类目、品牌和素材授权签字。
- 上一已验证版本、回滚负责人和回滚演练结果。

不得把 AppSecret、完整设备 ID、标签正文、条码/二维码值或用户图片放入发布记录。

## 6. 上传与环境晋级流程

### 6.1 dev → qa

1. 冻结候选 commit，确认无未解释生成物和调试开关。
2. 在干净环境完成第 4 节命令；全部通过才可进入开发者工具。
3. 使用授权 AppID 导入项目，确认 `miniprogramRoot`、基础库和编译设置。
4. 开发者工具完成编译、模拟器主旅程和真机预览；记录所有 warning，并验证相机扫码、相册、文件与蓝牙权限的按需申请和拒绝恢复。
5. 由授权人员上传开发版，版本号与候选版本一致；当前没有自动化上传命令可用。

### 6.2 qa → uat

1. 执行 `TEST_PLAN.md` 的候选回归、扫码权限与实物码、存储迁移/恢复和 Android/iOS × 打印机矩阵。
2. 所有 P0/P1 关闭，或 P1 例外有产品、QA 双签和明确到期时间。
3. 生成体验版并仅邀请已知验收人员；使用脱敏标签数据和专用耗材。
4. 至少运行一个业务日，收集连接、打印、存储和 UI 证据。
5. 产品、QA、硬件和法务/内容负责人签署 UAT 结论。

### 6.3 uat → prod

1. 确认主体、名称、图标、类目、隐私保护指引、权限用途和全部资源授权。
2. 提交平台审核；审核反馈必须形成缺陷或变更记录，不能在未回归的临时包上直接发布。
3. 审核通过后再次核对待发布版本与已验收 commit、包体和配置一致。
4. 发布负责人和复核人共同执行平台发布操作。
5. 使用专用设备完成 1 张标注“上线冒烟”的标签，不在生产做批量压力测试。

## 7. 灰度与观察

灰度按“受众 + 观察窗口 + 退出条件”管理：内部体验人员 → 5–20 名邀请用户 → 生产放量。平台账号是否提供原生百分比灰度能力必须在发布时由管理员按当期能力确认；若不支持，不得在记录中虚构 10%/30% 技术流量控制，可通过受控邀请、发布时间窗口和客户范围管理风险。

每档放量前记录扫码结果类别/失败码（不含原文）、连接尝试、握手、打印成功/失败、重连、存储失败和客服反馈。当前没有远程遥测后端，只能使用脱敏测试报告和人工汇总；在隐私披露与用户同意完成前不得临时接入埋点。

任何数据丢失、错打/重复打印、主流程不可用、隐私或授权问题立即停止晋级。普通失败率阈值应在首轮 UAT 建立基线后由产品、QA、硬件负责人填写，不能凭空设定。

## 8. 回滚流程

### 8.1 触发条件

- 任一 P0：无法启动、数据损坏/丢失、广泛错打或重复打印、隐私泄露、品牌/素材授权异议。
- P1 集中爆发且无安全绕行路径，例如某主流机型持续握手失败或存储恢复不可靠。
- 平台审核、权限或包体配置与验收版本不一致。

### 8.2 执行步骤

1. 冻结继续放量和新上传，记录开始时间、影响版本、设备/机型范围和首个证据。
2. 打印异常先通知用户停止重试；已开始发送的任务不得自动重放。
3. 在受控测试设备上可设置本地 `ble_reconnect_off` 并断开连接，止住自动重连。该键不能远程覆盖已安装用户，且人工选机仍可直接连接，因此不是全局停印方案。
4. 由发布负责人按当期微信后台能力恢复到上一已审核、已验证版本，或撤回/暂停受影响版本；具体平台操作和操作人写入发布记录。
5. 验证 schema v2 数据仍可被回滚版本读取。禁止把“清空微信数据”作为常规回滚手段。
6. 回滚后用专用数据执行启动、项目读取、连接和单张打印冒烟，确认后再通知恢复。
7. 完成影响范围、根因、数据修复、补充测试和再次发布条件的复盘。

## 9. 部署前后检查

### 部署前

- [ ] 候选 commit/版本、依赖锁、工具版本已记录，工作树干净。
- [ ] `npm ci`、`npm run verify`、覆盖率与本地包体通过。
- [ ] 正式 AppID、成员权限和开发者工具版本已确认，无秘密入库。
- [ ] 微信编译/预览/上传报告通过；所有 warning 有处置结论。
- [ ] 真机 UI、相机扫码、BLE、打印、迁移和回滚矩阵有证据。
- [ ] 隐私、类目、品牌、模板、素材和第三方 notice 完成签字。
- [ ] 上一稳定版本、回滚负责人、沟通渠道和观察阈值已确认。

### 部署后

- [ ] 生产版本号、发布时间和操作人已记录。
- [ ] 专用设备单张冒烟通过，未使用真实敏感内容。
- [ ] 观察窗口内人工汇总连接、打印、存储和投诉情况。
- [ ] 无 P0/P1 触发；若触发已停止晋级并执行回滚。
- [ ] 关闭发布窗口时记录遗留项、负责人和复盘日期。
